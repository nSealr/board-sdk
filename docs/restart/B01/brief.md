Do not create an empty crate hierarchy, a universal HAL, a plugin manager, a new orchestrator or a second cryptographic implementation.

Use existing maintained Rust interfaces when they match a concrete consumer; compare actual embedded bus/I/O/display/entropy interfaces and selected driver semantics, including errors, async cancellation and licensing. ## Required observable contracts

**SDK-01 — dependency direction.** Board SDK imports neither `nsealr-core`, Nostr schemas/accounts/kinds/policies nor the client TypeScript SDK. Nostr applications consume Board SDK services through concrete adapters. Hardware supplies a versioned electrical contract; it does not import application code. Use immutable revisions/package artifacts, never sibling filesystem assumptions or mutually importing repositories. Keep the repository name `board-sdk`; `@nsealr/sdk` is a different, host integration package. No public registry publication is part of B01.

**SDK-02 — service responsibilities.** Cover buses, power, fallible entropy, key handles/algorithms, storage, display, input and lifecycle. For each service give real caller/owner, input/output ownership, maximum transfer/work/time/state, cancellation/reset behavior, errors, retained sensitive state and actual implementation/qualification owner. Distinguish semantic requirements from numerical values that await target measurements. Proposed APIs must not silently claim a concrete timeout, pin, algorithm or driver that was not reviewed.

- Bus and expansion access respect exact voltage, startup/pull/reset, power and pin ownership. Private SE and review buses cannot become unrestricted expansion handles. No universal display FPC or 5 V GPIO compatibility is assumed.
- Entropy is fallible all-or-error; any error invalidates/wipes the entire caller destination and yields no secret/crypto output. No silent cached, deterministic or weak fallback. Preserve S02 provider provenance, finite waits/retries and actual linked/invoked provider proof. A cooperative outer timeout cannot bound a blocking poll hidden inside a driver.
- Key handles identify custody location, exact algorithm/parameters/purpose and epoch/lifetime. They do not imply native BIP340 support, non-exportability, human consent or protection from hostile firmware. Session/reset/owner changes invalidate applicable handles; reject stale/foreign handles before operations. Original application identity recovery remains the application/protocol's responsibility; do not normalize or convert private scalars implicitly.
- Storage states atomicity, corruption/rollback/crash behavior and durable completion. A successful write or AEAD tag alone does not prove antirollback or erase. No common reset promise may conceal surviving SE objects, vendor roots or a terminal counter.
- Display services transfer/render buffers and report their actual completion/error semantics. Input services report device-owned events/time; they cannot mint Nostr authority. Exact DMA/bus/pin/master ownership and local physical proof remain necessary for a trusted review claim. A framebuffer hash or mocked button cannot establish it.
- Power/reset/update paths enumerate which hardware, secrets, authorization, channels and partial outputs survive. Cancel/error must not leave a stale result eligible for later release. Recovery must have a bounded documented outcome rather than retry forever.

**SDK-03 — electrical/version contract.** Define how a caller pins exact board revision, hardware commit/artifact digest, MCU/package/revision, SE applet/configuration, connectors/pins/rails/limits, driver/features and boot/update roots. Distinguish static hardware capability, local runtime state and accepted release evidence; none is a global trusted boolean. Incompatible/unknown tuples reject explicitly. Define which changes require driver, electrical, lifecycle and physical requalification.

There is no admitted custom electrical contract yet. Do not fill illustrative pins from an inherited BOM or call a placeholder qualified. H04 supplies the reviewed actual contract; B02/B03 prove actual services. If the literal B01 electrical-pinning criterion cannot be satisfied before that input, record the affected criterion as pending with H04 as its prerequisite and do not mark B01 complete. An API decision can be accepted as a bounded partial result without weakening the parent criterion or inventing a circular platform dependency.

**SDK-04 — firmware/owner lifecycle.** Specify developer, owner-secured and product-qualified conditions and the trust/secret-reset transition rules. Separate actual hardware enforcement from external release admission: “product-qualified” is not a command/flag that grants security. Initially one trusted firmware image; library types provide no hostile-application isolation. Distinguish MCU owner roots, off-device signing/recovery credentials and immutable/vendor SE applet/update roots.

Enumerate manufacture/development, first enrollment, normal lock/unlock, authenticated same-owner firmware update/root rotation, interrupted update, reset/power loss, rollback attempt, lost owner credentials, destructive reset, new owner and hardware replacement. For each give preconditions/authority, affected objects, durable ordering/failure state, residual privileges, supported retry/recovery and the physical proof owner. No universal safe reset, irreversible setting, PIN protocol or SE composition is selected here. Reconcile concrete S04 protocol and H01 host rules before any lifecycle implementation. A finite/irreversible object budget that makes an ordinary programmable Board practically disposable is an explicit product incompatibility requiring a reviewed decision, not a hidden acceptable default.

**SDK-05 — a useful implementation only when used.** B01 documents the API/extraction decision. If its implementation requires a real crate/example, first identify the actual selected consumer, exact source/toolchain/features and writable scope in an accepted addendum. Build a clean standalone non-Nostr consumer without `nsealr`, sibling checkouts or success-returning hardware stubs. No new executable source is authorized by this documentary brief. B02 owns selected development-hardware driver/service proof; H08/H09 and B03 own actual custom-assembly and independent developer release evidence.
